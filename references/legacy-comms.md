# 参考：机器间沟通记事本（自由文本通道；含读位 read cursor）

> 本文件是 `workbuddy-sync-all` 技能的参考文档，由 SKILL.md 拆出（内容与原文一致）。


> **定位（2026-10-14 定稿，两套通道并存）**：本记事本**不是**历史/只读通道，照常读写。
> 判据一句话：**要回执/要闭环走 `wbsync a2a`；要人读/要广播走 `wbsync comms`。**
> 同一件事不要两边各发一份完整指令——A2A 放任务 + 一句话指针，正文留在本记事本。
> 文件名里的 `legacy-` 是历史遗留，内容是现行有效的。

**目的**：让各台机器的 WorkBuddy Agent 能**自动互相留言、互相交接任务**，不用用户在两台机器之间来回传话。

**位置**：`wb-coop/shared/机器间沟通-<后缀>.md`（每机一个专线文件，随 Syncthing 自动双向同步）。

> **★ 最高优先级约定：本机 Agent 每次被唤醒（用户打开对话、或提到同步/多机相关的事），
> 第一件事就是跑 `wbsync comms check`，看有没有别的机器留给本机的、还没回复的消息。**
> 有 → 立即执行并追加回执（状态「已完成/已回复」）；没有 → 继续正常服务。这是硬约定，不是可选项。
> 用户不应该需要手动提醒「去看看有没有留言」——Agent 自己就要主动查。

**核心约定（每台机器的 Agent 必须遵守）**：

1. **每机一个专线文件（根治并发冲突）**：本机只写自己的文件 `机器间沟通-<本机后缀>.md`
   （A 写 -A、B 写 -B），读对方留言时读对方的专线文件。**绝不共写同一个文件**——多机同时编辑
   同一文件必然触发 Syncthing 冲突（一方被降级成 `*.sync-conflict-*` 副本），导致「写了对方说没收到」。
   历史文件 `机器间沟通.md` 已冻结为归档，不再写入。
2. **固定消息格式**（方便机器识别方向与状态）：
   ```
   ---
   ## [A→B] 简短标题（状态）（时间：YYYY-MM-DD HH:MM）
   正文：说清楚要对方做什么、何时需要回复。
   ```
   - `[A→B]` 是方向标记：谁发 → 发给谁；`[全员]` 表示发给所有机器。
   - 状态标记只允许标准词：`待回复` / `已回复` / `已解决` / `已完成` / `已确认`。
     其他说明文字（如「请遵守」「准实时」）一律放正文，不要放标题括号里——否则会被误判为状态。
3. **被唤醒即主动扫**：本机 Agent 每次被唤醒（打开对话、提及同步/多机），第一件事就是 `wbsync comms check`
   （它会自动扫描所有专线文件、跨文件配对），看到「发给自己的、还没回复」的消息就处理并追加回执。
4. **回执必须「指向原消息」**：回复别人时，用 `wbsync comms send --to X --reply-to <原消息标题> ...`，
   回执正文末尾会自动标注 `↳ 回复：<原消息标题>`，并自动把原消息状态改为「已回复」实现闭环。
5. **不新建散文件**：跨机沟通统一走专线文件，不要再各自新建 `给A机的…md`、`回复B机…md` 这类散文件。
6. **只放跨机协作的事**：纯本机小事不写进来，避免噪音。
7. **读位记己不记人**：本机读到各机的位置只写在本机专线文件里（`wbsync comms cursor` 查看），
   读未读用 `wbsync comms read --peer <机>`（读完自动推进）。**不要**为了「看有没有新留言」
   每次都整份重读对方的专线文件——那是纯浪费；也**不要**去改对方的文件。

**两个「必看」触发时机（务必落实）**：

1. **每次打开对话时**：SessionStart hook 会拉起 Syncthing，并把 `comms check` 结果落盘到
   `$TMPDIR/wbsync-comms-unread.json`；Agent 在会话一开始就应主动跑 `wbsync comms check`
   （或读那个提示文件），有留言就主动告诉用户并处理。
2. **刚建立连接/新机器加入时**：配对成功、`workspace init`、或首次 `setup` 完成后，立即跑
   `wbsync comms check` 扫一眼，确认有没有需要本机接手的待办。

**命令**：

```bash
wbsync comms check                    # 看发给本机的、未处理留言（人类可读）
wbsync --json comms check             # 同上，JSON（供 Agent 脚本化读取）
wbsync comms send --to B --title 标题 --body 正文 --status 待回复   # 给 B 机留言
wbsync comms send --to 全员 --body 通知内容                          # 给所有机器留言
wbsync comms send --to A --title 回执 --body 已处理 --reply-to "原消息标题"  # 回执（自动闭环原消息）
wbsync comms cleanup [--apply]        # 归档已闭环旧消息到 机器间沟通-归档.md
wbsync comms cursor                   # 看本机读到各机哪里、各机还有几条未读
wbsync comms cursor --mark [--peer B] # 把读位推进到最新（标记为已读）
wbsync comms read --peer B            # 只输出 B 机未读的留言，读完自动推进读位
wbsync comms read --peer B --all      # 输出 B 机全部留言（不推荐，除非要重读）
wbsync comms read --peer B --no-mark  # 输出未读但不推进读位
```

**读位（read cursor）—— 2026-10-14 新增，专治「每次都把对方整份专线重读一遍」**

- **它是什么**：每台机器记录「本机读到各机专线的第几条」，写在本机专线文件里的
  `## 读位` 区（`<!-- wbsync-cursor … -->` 注释块）。**只写本机文件，绝不写对方文件。**
- **位置用「第几条」不用时间戳**：专线只追加，序号稳定；时间戳只到分钟，同一分钟两条会漏读或重读。
- **带标题校验**：读位同时记下已读末条的标题；对方文件若被归档/重排，序号语义会漂移，
  此时报「读位漂移」并按**保守位置**输出（宁可多读，不可漏读），提示重读后用 `--mark` 重置。
- **未初始化时**：该机全部消息**视为未读**（不猜「应该都读过」，避免静默漏读）；
  确认确实读过，跑 `wbsync comms cursor --mark --peer <机>` 置零。
- **典型用法**：会话开始跑 `wbsync comms check`（末尾会附一行未读概览）→ 有未读就
  `wbsync comms read --peer <机>` 只读未读 + 自动推进 → 不必再整份阅读对方的专线文件。
- **归档兼容**：`comms cleanup` 保留文件头（读位区在文件头里），归档不会动读位。

**回执闭环（`--reply-to` 的工作方式）**：每机专线机制下**绝不写别人的文件**，闭环靠「标题配对」自动判定：
- 回执时带 `--reply-to <原消息标题>`，会在回执正文末尾写一行 `↳ 回复：<原消息标题>`；
- 各机 `comms check` 时，会把「`↳ 回复：X`」或「同标题回执」识别为 X 已闭环，不再列「待我回复」；
- 本机发出的消息若已获对方回复，本机 `comms check` 会**只改自己的文件**、把它标为「已回复」（自闭环）。
这样既实现闭环，又做到零跨文件写、彻底避免冲突。

**状态词约定（务必遵守）**：消息标题里只有**第一个括号**可放状态词，且必须是标准词
（`待回复 / 已回复 / 已解决 / 已完成 / 已确认 / 已关闭`）。其他说明文字（如「请遵守」「准实时」）
一律放进正文，不要放进标题括号——否则会被误判为状态。

**每机专线 + 历史文件**：本机写 `机器间沟通-<本机后缀>.md`（如 A 写 `-A.md`），
读对方留言读对方的专线文件。`机器间沟通.md` 为历史归档（已冻结，只读不写）。

**首次建立时机**：任意机器首次 `setup --apply` 或 `workspace init --apply` 后，若本机专线文件
（`wb-coop/shared/机器间沟通-<后缀>.md`）不存在，就自动创建它（含沟通约定模板）。之后各机 Agent 遵循上述约定即可。
